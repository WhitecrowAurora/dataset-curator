# 发色标注质量与流程验收

2026-11-19，H:\tagger。本轮继续此前接入，按用户的“尽量沿用原操作，推理过程中尽量不增加手动步骤，无法解决的冲突必须人工审核”验收。未提交或推送，保留原工作区改动。

结论：有限样本下，标签→描述→发色复核→人工决定/撤销→续做的流程可用；本轮确认的回归已修复。银、灰、白仍需要保留人工裁决，不能把70%模型输出当作70%正确率。普通长描述存在细节猜测，尚不具备逐句准确性或全量数据集准确率的结论。

## 操作

首次在「模型管理」的「发色与动漫复核」下载三个模型；已有 Torii 可继续使用原路径，也可一键使用下载后的精确 GGUF 路径。在「冲突与决策」的折叠设置中保存默认选项。之后沿用新任务→启动→运行页→结果的操作；系统自动完成标签、描述及发色阶段，不要求确认模型切换。运行页和底栏显示当前阶段；发色复核没有逐项进度契约，因此显示运行状态，不用标签阶段的100%冒充整批完成。

「冲突与决策」默认只显示待处理项，设置及单图测试折叠，可按任务筛选。每图保留分类器前三候选、各自概率和发色示意；VLM建议不伪造概率。浅色组可直接选择银/灰/白/金。人工确认后写回标签并从待办消失，刷新保留决定；撤销恢复原发色标签，保留描述及其他标签。多人可以框选角色复核并合并结果。必要的人工待办数量不作为“不无感”的判据。

## 真实任务

用户GPU有游戏等占用，本轮真实模型执行均使用CPU，未修改生产GPU配置，也未停止其他窗口的服务。模型请求串行。使用默认生产描述质检，没有放宽阈值；CPU请求曾因120秒等待超时而自动重试，最终成功。CPU延迟不能用于推断GPU速度。

## 历史难例回放

此前审查指出的18份无头发误接受与8份非人物误接受，本次回放没有继续自动接受的项；多数变成人工审核，并不意味着全部自动正确跳过。自动接受的8项已看图核对：26棕、32黑、56金、58绿、103黑、116黑、201蓝、portrait浅金；没有发现明显物体发色污染，其中portrait的浅金/灰阴影仍有主观边界。这是小样本视觉抽查，没有全量人工真值，不能给出数据集准确率。见 [replay.json](replay.json)、[accepted-contact.jpg](accepted-contact.jpg)。

## 已修复的确认问题

- 标签和描述共用外部资源监控器时，标签阶段提前停止线程，描述阶段重新start报“threads can only be started once”。客户端只停止自己创建的监控器，任务统一管理共享实例。
- VLM末轮颜色与低置信分类器相同时可能自动通过。现在支持最终颜色的分类器必须达到阈值；light不能确认银/灰/白/金。
- Torii解析把眼睛高光、黑白衬衫误当头发歧义或灰度，漏掉“Blonde girl with ... hair”，并把部分动物/物体当人物。缩小解析范围并完善相关识别；仍是启发式提取，不是人物检测器。
- 切换模型文件或别名可能复用旧模型进程。复用检查包含权重/投影路径、文件大小和修改时间及别名，停止后清空指纹。
- 复核切换停止主托管服务后没有恢复。仅在实际切换时停止，任务结束恢复原配置；本地标签任务也走同一生命周期。失败恢复有日志，标注产物保留。
- 续做关联可能覆盖人工决定或丢失旧任务关联；原图变动仍沿用旧复核。关联改为事务更新，保留历史任务与人工决定，核对图片hash。
- 按image_id回写可能改动没有复核ID的历史分片，甚至无匹配也重写字节。仅明确定位允许旧分片补配，没有本批关联则跳过历史分片。
- 人工回写与批结算可能竞态覆盖。共享回写锁内重新读取记录，人工决定和批结算串行。
- 图片缺失可能打断整批，VLM不可用的review缺重试入口，停止后复核可能一直pending。分别单项失败、开放重试并结算停止状态。
- 新任务默认选项异步恢复有竞争；冲突页先打开后不自动出现新记录；运行页把新阶段写成打标中并沿用完成百分比。已修复默认恢复、轮询/过期响应、待办筛选和阶段显示。
- 旧客户端替身收到空parts_env新关键字导致兼容检查失败。仅新分阶段流程传入该参数，旧调用保持原形态；没有修改原测试掩盖错误。

代码按发色领域、运行时、存储、Web桥接和现有UI组件划分；未增加训练器或launcher入口。

## 模型与依赖管理补齐

独立复核组件/后端模块接入原模型管理，不把专用发色包混入通用tag后端菜单。两个ONNX模型各自下载固定revision的model.onnx与meta.json，落到models/hair-color/<模型名>；Torii下载已验证的DraconicDragon社区GGUF Q6_K与FP16视觉编码器，落到models/nl/torii-gate-0.5。来源、revision、缺失文件与位置可见，使用现有下载源、代理、进度和取消接口。Torii可一键保存明确权重文件，保留其他复核设置；默认路径可直接运行，已有E盘路径不会被静默改掉。

下载器支持固定revision，清单、单连接与分段下载一致；旧模型仍默认main。复核包核对所有必需文件与精确字节数，半文件/过大文件不能算就绪；不宣称每次目录扫描做了SHA256校验。官方固定revision清单已实时核对，现有下载器真实下载MobileNet meta.json成功，标签顺序一致，见model-download-evidence.json。未重复下载4.6GB Torii；浏览器下载/取消使用受控fixture，设置持久化使用真实隔离存储。

install.bat继续委托devtools/setup_embedded_env.ps1；Windows安装后把ONNX Runtime纳入必需导入检查。install.sh修复只检测torch/transformers/timm就提前跳过的问题，缺ONNX时补其余依赖并复用可用torch/torchvision。保留SkipTag/NoLlama选项。requirements-tag.txt已有onnxruntime，其他图像/HTTP/缓存依赖已有基础清单，新增pyproject hair extra并在原依赖管理显示为共享包：onnxruntime、pydantic、numpy、Pillow、huggingface_hub、httpx、psutil。Torii复用llama-server，不添加llama-cpp-python或未实现native依赖。

PowerShell AST与bash -n通过；Linux“已有torch、缺ONNX”的实际shell分支在mock Python下验证只安装其他依赖，未重建或全量安装用户环境。101项检查见models-deps-tests.xml，完整性补验见download-integrity-tests.xml，浏览器见browser-models-results.json与models-review.png/deps-hair.png。浏览器早期失败来自测试定位器（输入值随编辑变化、标题含计数），修正后全部通过。最后新增pydantic显示项已核对实际snapshot与导入。

## 范围

没有“零bug”或“全量标注准确率通过”的结论。银灰白、多人、灰度及模型猜测继续人工审核；颜色示意辅助比较，不是严格色值边界。只改变发色标签，普通caption不会因人工选色被自动重写。普通描述和独立发色复核仍分开请求，续做也可能先初始化模型再跳过，计算步骤不等于新增用户操作步骤。

RAM缓存的16/32/96GiB模拟检查通过，GGUF只是可回收文件页缓存，不是已加载CPU模型常驻。百万级PNG存储、历史关联查询/分片重读和混合来源普通描述逐图路由尚未验收；应用内锁不提供跨窗口GPU仲裁。本輪未重新做GPU性能基准。Torii native尚未实现。

临时测试脚手架、测试状态与日志完成后归档至 `.delete/hair-quality-tests-20261119/backend/smoke/hair-quality`；本目录保留结果与截图。其他窗口服务不动。
