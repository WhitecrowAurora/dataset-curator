# 发色复核流程：性能开销估算

结论：两个专用分类器开销较小，主要成本是额外 VLM 请求和重复加载 PixAI。如果本来就要生成 caption，优先复用其角色描述；只让尚未解决的冲突进入一次独立复核。批量处理按阶段复用模型、GPU 串行，不按每张图片切换模型。

本次只读核对源码，并对先前真实测试结果做离线统计，没有新增 GPU 任务或修改生产代码。数值来自本机 RTX 4070 Ti SUPER 16 GB、CPU ONNX 四线程、PixAI GPU BF16 batch=2，以及 llama.cpp 单 slot Q6_K。估算使用平均耗时，不将单图中位数当作批量平均。

## 实测组件成本

| 组件 | 平均单图耗时 | 使用口径 |
| --- | ---: | --- |
| PixAI | 0.256 s | 120 张原图，GPU BF16，batch=2，已加载 |
| MobileNet | 0.0168 s | CPU 四线程，118 个热运行样本 |
| CAFormer | 0.2328 s | CPU 四线程，118 个热运行样本 |
| ToriiGate | 2.764 s | 126 张混合输入，官方精简 JSON 完整描述 |
| Qwen3-VL | 1.318 s | 同 126 张输入，现有短发色 JSON |

Torii 主测试中的 8 个动漫重点例平均 3.644 s，5 个多人动漫例平均 4.331 s；这两组很小，不代表均衡动漫集，但说明动漫群像的描述成本可能高于混合输入均值。不能拿短发色 Qwen 的耗时当作真人完整 caption 的耗时。

PixAI 两次加载为 10.09 / 9.64 s。CPU 分类器首次调用包含 session 初始化：MobileNet 约 0.18 s、CAFormer 约 1.65 s。先前服务日志中从开始加载到模型就绪，Torii 约 3.09 s，Qwen 约 4.67 s；这是已缓存文件下的单次日志差值，不包含新下载、进程全部启动成本或普遍冷启动统计。

## 假设不同复核比例

串行、模型已加载且复用的推理阶段估算：

`平均每图时间 = PixAI + MobileNet + CA调用比例×CAFormer + 额外VLM请求比例×VLM`

以下假设 70% 图片需要 CAFormer；10% / 30% / 50% 是额外 VLM 复核比例。70% CA 调用比例与“置信度阈值设为 70%”是两个独立概念。表格分别估算所有复核都使用一种 VLM 的情况，实际按动漫/真人混合路由时需要加权。

| 额外 VLM 复核比例 | 使用 Torii：平均秒/图 | 使用 Torii：1 万图 | 使用 Qwen：平均秒/图 | 使用 Qwen：1 万图 |
| --- | ---: | ---: | ---: | ---: |
| 10% | 0.712 | 119 分钟 | 0.568 | 95 分钟 |
| 30% | 1.265 | 211 分钟 | 0.832 | 139 分钟 |
| 50% | 1.818 | 303 分钟 | 1.095 | 183 分钟 |

这些不是新流程的端到端吞吐实测。未计下载、读盘、解码、数据库写入、封包、人物检测/头发分割、模型切换等待和人工时间；保留串行阶段相加口径，不假设并发加速。此前不同批次与模型配置的结果用于成本估算，最终落地需同批端到端验证。

如果已有一次适合的分角色 caption 可复用，不新增 VLM 请求，在同样 CA 调用比例下，两个专用分类器合计增加约 0.180 s/图，即 1 万图约 30 分钟；原有 PixAI、caption 的成本还要另算。若每图两个分类器全跑，则分类器增加约 0.250 s/图，即约 42 分钟/万图。复用同一份 caption 是属性提取，不是独立看图复核；未解决的冲突仍可能新增请求。

## 将 70% 阈值加入现有规则的离线回放

120 张之前测试的原图：保留当前级联的其他逻辑，只给 MobileNet / CAFormer 的提前接受条件各加一项“首选分数 ≥0.7”。此回放不包含新的人物/可见头发判据，也不把不可靠的旧规则当成生产建议。

| 条件 | CAFormer 调用 | VLM 调用 |
| --- | ---: | ---: |
| 原型现有规则 | 85/120（70.8%） | 76/120（63.3%） |
| 提前接受再要求 ≥70% | 92/120（76.7%） | 86/120（71.7%） |

按真实被触发样本对应的 VLM 单图耗时、CPU 热运行均值和 PixAI 批均值估算：原规则全部使用 Torii 约 382 分钟/万图，使用 Qwen 约 213 分钟；加阈值后分别约 419 / 233 分钟。两者都是假设替换复核模型后的串行成本估算，未运行新级联，也不证明识别准确率提高。

样本混有商品、风景、动物，实际动漫占比较少。先明确有无可见头发和角色数量可减少无效工作，但相应检查的成本与最终调用比例尚未测量，不能假设它免费或可靠。

## 当前代码中影响批量性能的点

1. 单图 `pixai_predict` 每次构造、加载、运行、释放 backend。当前原型便于隔离单次任务，但若直接逐图调用做批处理，会反复支付近 10 s 的历史加载成本，还可能触发仓库 metadata 查询。批量链应在已有执行层复用 backend 和同次打标结果。
2. 级联 `elapsed_ms` 从取得 PixAI 结果之后才开始；原型界面记录不能当完整端到端延迟。
3. 两个 ONNX session 现已缓存，热调用不反复加载。CPU 四线程成本不占 GPU 显存，但占用 CPU 时间与 RAM；本次没有测 RAM 峰值。
4. 主 PixAI `predict_batch` 默认不保留全量原始分数。直接开启 `snapshot_scores` 会额外调用 `_full_scores` 再前向一次。发色接入应从原始同一次前向保留必要头发/人物分数，并保持现有打标阈值、输出与类别语义，不能为取十几个分数重跑整个网络。本次仅指出成本，没有实施改动。
5. 图片类型按数据集或来源配置分配，混合来源允许覆盖；若新增一个 GPU 风格分类器，要单独测它的开销和误路由率。
6. 本机建议按批次运行 PixAI → 释放 → 动漫 Torii → 释放 → 真人 Qwen。不要逐图轮换两套 VLM。所有 GPU 阶段串行，启动前检查其他窗口任务；这里没有新增跨窗口互斥代码。

模型运行后的整卡显存占用最大采样为 Torii 6592 MiB、Qwen 10329 MiB，分别来自独立运行，包含桌面进程，不是模型净占用或连续监控峰值。不要把两者直接相加作为共驻显存预测；16 GB 机器优先单个 VLM，PixAI 是否共驻要单独验证。本估算没有 CPU+GPU 重叠执行收益，也没有增加 slot 或 batch 的吞吐承诺。

详细输入、公式和阈值回放结果见 [analysis.json](analysis.json)。来源为已保存的 `hair-color-packs-20261119` 和 `toriigate-evaluation-20261119` 报告，以及当前 `tagger/hair_color`、`tagger/cpu_tagger.py`、`tagger/client.py` 源码。没有新增测试脚手架、后台服务或生产逻辑。
