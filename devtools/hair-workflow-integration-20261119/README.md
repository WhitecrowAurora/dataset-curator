# 发色流程与自适应内存缓存接入验收

2026-11-19，项目 H:\tagger。本阶段接入运行流程和 WebUI；Torii native 引擎优化留待下一阶段。没有提交或推送，原有工作区改动保留。

## 使用

1. 打开 WebUI「冲突与决策」，在「发色复核设置」指定 Torii、Qwen 的模型目录或 GGUF 文件。多个量化版本共存时直接选具体 GGUF，同目录必须有对应 mmproj。本机测试 Torii 在 E:\dev_model\ToriiGate-0.5，生产默认不硬编码该盘符。
2. 缓存上限和系统余量设为 0 时自动决定；可以手动限制缓存，并查看预算、保留条目及释放空闲缓存。
3. 新任务勾选「复核发色并更新标签」。需要按数据类型生成普通描述时，再勾选「描述使用动漫 Torii / 真人 Qwen」。选择动漫、真人或混合/未知来源。
4. 主标签阶段结束后串行复核；有分歧的图片进入「冲突与决策」。候选展示分类器前三项概率与发色示意，浅色可选择银、灰、白、金。人工决定写回标签，撤销恢复原始颜色标签，保留长发等属性和 caption。
5. 多人图片可以框选各角色头部、分别确认，再显式合并角色发色到原图。多个角色的不同发色不自动追加单人物的 multicolored hair 标签。

## 内存策略

按实时可用 RAM 和条目估算大小保留 LRU 空闲缓存；默认系统余量为 max(2GiB, 总 RAM 的20%)，缓存预算不超过总 RAM 的50%，手动上限进一步收窄。后台每5秒检查压力，正在使用的条目不回收。

PixAI 可保留 CPU 模型，两个专用分类器保留 CPU ONNX session；Torii/Qwen GGUF 保留只读文件映射并预热系统文件缓存，阶段结束停止推理服务以释放显存。文件页可以被操作系统回收，**不等于已加载 VLM 常驻 CPU，也不能保证省掉引擎初始化和传入显存**。估算大小不是进程 RSS，运行模型的峰值分配仍在缓存预算之外。

16/32/96GiB 是模拟不同总量与可用量的压力测试，未在这些实体机器分别测试。因此不承诺“16GB留一个、32GB留三个”；数量还取决于其他软件和模型大小。映射文件不被计成已消耗的常驻内存来扩大预算，也不会假定释放映射就释放同等物理 RAM。

## 边界与下一阶段

- 两个专用模型只有10类，银/灰/白/金统一为light。概率属于各分类器自身，VLM文字建议不生成概率；70%是继续复核阈值，不是准确率。
- AnimeSeg不是头发语义分割，本次没有默认接入不稳定的头发mask；角色框选可用。批量默认头发可见性未知，因此往往继续VLM，这比早期假设10%冲突的成本高。
- 明确动漫的普通描述使用Torii，真人及混合/未知普通描述使用Qwen；混合数据普通描述尚未逐图分组。发色复核会按每图来源分组。
- 普通描述和独立发色VLM复核目前分别请求，未实现复用描述以减少请求；标签/描述阶段也可能重复读取包或HF输入。旧性能估算不包含这项额外开销。
- 分片回写已改为批结算一次更新，人工单项决定仍更新其关联分片。复核图片当前逐图保存PNG，全量百万级输入的磁盘、索引、重读和回写性能尚未验收；优先用于有限批次。
- 托管服务产物记录真实GGUF路径、量化文件名、引擎及运行时文件指纹；没有可验证revision时明确留空。外部服务精度/路径未知，不引用旧主服务指纹。
- Torii本机使用社区Q6_K GGUF；未证明与原始BF16精度一致，也未证明动漫识别准确率显著高于Qwen。
- 下一阶段：先按相同图、相同官方提示词、相同像素/生成长度建立llama.cpp基线；确认Qwen3.5-4B混合linear/full attention与视觉投影支持，再实现native。现有Qwen3-VL native不能直接套用。验收先做输出质量与银灰白回放，再比较首图延迟、吞吐、RAM/VRAM和CPU/GPU迁移。没有“native一定更快”的结论。
