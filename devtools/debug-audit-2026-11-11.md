## A01 / P1：本地打标或封包失败仍标为完成

位置：`tagger/web/jobs.py:1722-1733`、`tagger/web/jobs.py:2111-2126`。

本地 `_run` 仅检查停止与 busy，不检查 `job.stats.failed`，随后运行封包并写 `done`。`_pack_phase` 记录失败、缺失计数，却只将主动停止或资源中止转换为非成功终态。

复现结果：

| 情况 | 打标完成/失败 | 封包写入/缺失/失败 | 最终状态 | error |
|---|---|---|---|---|
| 1 张图的后端推理全部抛异常 | 0 / 1 | 0 / 1 / 0 | done | 空 |
| 1 张坏图，后端返回标签，封包解码失败 | 1 / 0 | 0 / 0 / 1 | done | 空 |

两种情况都没有正式分片，页面却可以显示“已完成”。而且 `_run` 收尾会按 `done` 清除恢复记录。即便允许保留部分成功样本，完全失败也不应显示成功。

建议：在现有编排层统一解释打标与封包结算结果；存在实际失败或预期产物缺失时给出明确非成功状态与原因。是否允许部分成功继续封包，应按当前业务口径处理，不能由“循环结束”自动等同于成功。

## A07 / P2：首次 WebSocket 连接失败不启动持续轮询

## A08 / P2：旧任务的轮询结果覆盖并关闭新任务订阅

切换任务只关闭 socket/计时器，已发出的旧 HTTP 请求仍会返回。轮询 await 后未确认当前订阅身份，直接 push；终态结果还调用全局 `closeAll()`。

运行真实 store 代码复现：

1. 订阅 A，WS 断线后轮询 A；让其 HTTP 请求保持未返回。
2. 切换订阅 B，创建 B 的 socket。
3. A 的旧请求返回 `status='done'`。
4. store 中 `jobId='b'`，但 `snap.id='a'`，A 的事件混入，B 的 socket 被关闭。

建议：按订阅生命周期隔离异步响应；返回后只允许仍属当前订阅的响应修改状态或关闭资源。只比较任务 ID 仍不足以处理同 ID 的重新订阅。

## 排查中排除的误报

- **更换模型/参数后默认跳过已有有效图片**：当前代码与近期机制记录明确要求只有“强制重做”才重新计算，属于现有设计；未作为 Bug。A02 针对的是主动执行过程中启用的内容缓存，不是已有产物跳过策略。
- **旧审计记录中的 5 个测试失败**：本轮完整测试没有复现，不能继续当成当前缺陷。
- **图片分片缺少画师字段（A03）**：用户确认画师信息单独分发，图片分片只承担图片流式读取，属于现有设计，已撤回原缺陷判断。
- **多画师 NL 和 TAG 覆盖范围不同**：当前 TAG 实现明确只注入第一位，NL 最多三位。存在与校验口径进一步统一的空间，未单独列为确定缺陷。
