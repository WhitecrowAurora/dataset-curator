## 2. 第二批：danbooru 768 分包（进行中）

**目标**：把 danbooru 素材统一成「面积预算 768²」的 JPEG，封成 1750 MB 的 tar 分片 + 逐图 `manifest.jsonl`。

**规则（`danbooru_build.py` 内实现）**
- `target_size()`：`面积 <= MAX_PIXELS` → 原样保留（`asis`，**不放大**）；长宽比接近某个预设桶 → 用桶尺寸（`bucket`）；否则按面积缩放并向下对齐 32（`freeratio`）
- 输出宽高尽量为 32 的倍数（SD VAE 要求），但 **`asis` 那批不保证**
- JPEG：`quality=QUALITY, subsampling=0（4:4:4）, optimize=True, progressive=True`
- 每片 1750 MB 封口，封口后有约 7.28 MB 的 tar 头/填充开销，正常

**断点续跑机制**
- 状态：`I:\anlia2\danbooru\_state.json`（`sealed` / `done` / `done_mark` / `manifest_bytes`）
- 启动时丢弃编号 ≥ `sealed` 的未封口分片，并把 `manifest.jsonl` 截断回 `manifest_bytes`
- 源分片缓存：`I:\anlia2\danbooru\images\*.tar`（处理完**不删**），下载中落在 `_cache\*.part`

## 3. 运维速查

所有外部命令都走执行器 `S:\tools\rc.ps1`（SSH 到执行机执行）。

**执行机地址只有一个地方要改：`S:\tools\rc.host`（一行 `user@host`）。**
写 IP 就直连；写域名会先查 A 记录拿到 IP 再直连（连接本身不走域名，无速度损失），解析到 IP 时会多打印一行 `TARGET ...`。已加 `StrictHostKeyChecking=accept-new`，换 IP 后首次连接不会卡在指纹确认。
（后续可选：在 Cloudflare 侧挂 DDNS，服务器每 5 分钟把 A 记录更新成当前公网 IP，TTL 设 60 秒；本地这边不用改任何东西。）

用法：

```
powershell -ExecutionPolicy Bypass -File S:/tools/rc.ps1 -Run <远端临时目录里的脚本名> -Timeout <秒> -Tag <标签>
powershell -ExecutionPolicy Bypass -File S:/tools/rc.ps1 -Path <本地脚本路径> -Timeout <秒> -Tag <标签>
```

- `-Run`：执行**执行机** `C:\Users\anlia\AppData\Local\Temp\<名字>`，脚本须先上传
- `-Path`：把本地脚本内容 base64 塞进命令行执行，**不用上传，但有约 8 KB 命令行长度的硬上限**，超了会报「命令行太长」
- 上传：`powershell -ExecutionPolicy Bypass -File S:\tools\upload.ps1 -Files <单个路径>`（一次只传一个，逗号列表参数会被当成一个路径）

## 4. 踩过的坑（按重要性）

### 4.1 ★ 数据集是 gated，必须注入 HF_TOKEN
`deepghs/danbooru2024-webp-4Mpixel` 是 **`gated:"auto"`**：**匿名请求一律 403**（`Access to dataset ... is restricted and you are not in the authorized list`），带 token 才 302 放行。token 在 `C:\Users\anlia\.cache\huggingface\token`（`ruilynx`，read 权限，有效）。

程序里虽有 `load_token()`（先读 `HF_TOKEN` 环境变量，再读 `~/.cache/huggingface/token`），但曾出现跑着跑着下载全部变 0 字节的情况。**修法：在启动器里显式 `set HF_TOKEN=<token>`**，别只依赖 `Path.home()`。

**故障症状（静默空转，最坑）**：`_cache/*.part` 全是 0 字节、日志**不打印 `[FAIL]`**、`imgs` 冻结、CPU 掉到 2~3%、`_state.json` 的 mtime 不再更新。缓存耗尽后就是纯空转，6 轮循环会白跑。

**诊断三板斧（30 秒定性）**
1. 带 token 手测：`curl -sSL --fail -C - -m 40 -o t.part -w "%{http_code}|%{size_download}" -H "Authorization: Bearer $tok" <resolve URL>` —— 正常应 40 秒约 838 MB / 22 MB/s；不带 token 对照必是 403
2. 看 `_cache/*.part` 的**精确字节数**（`Round /1MB` 会把几十 KB 显示成 0，要打印 `Length`）
3. 看 `_state.json` 的 mtime 是否在动

### 4.2 ★ 怎么判断"卡死"（连续误判过三次，务必按这个来）
`download()` 先写 `_cache/XXXX.tar.part`，用 `-C -` 续传，0 字节就等于从 0 开始；下完 `part.replace(final)` 改名进 `images/`。

**先记住三件事，否则一定会误判：**
1. **缓存耗尽时 `images/` 和 `manifest.jsonl` 会长时间冻住**。这一步要等整个源分片（~1.7 GB）下完才会继续出图，冻结十几分钟完全正常。**不能拿 `imgs` 不动当卡死证据。**
2. **`Get-ChildItem` 返回的 `Length` 有元数据缓存**，刚创建的文件可能长时间显示 0 或旧值。要看真实大小必须用 `[System.IO.FileInfo]::new($p).Length`／`[System.IO.Directory]::GetFiles()`，或者干脆用 `Measure-Object` 重新枚举。
3. **`curl` 进程存在 ≠ 在下载**。换 IP / 断网后连接会变成半开，`-m 3600` 会让它一直挂着不返回也不报错（实测挂 6~20 分钟）。

**唯一可靠判据**：用 .NET API 对 `_cache\*.part` 求和，隔 25 秒再求一次，看增量。
- 有增量（实测正常在 12~218 MB/s 之间）→ 健康，等着就行
- 增量为 0 且 `images/`、`manifest` 也都不动 → 才是真卡

**不要随便杀 `curl`**：杀掉会让对应的 worker 收到非 0 返回、直接 `[FAIL]` 掉那个分片（虽然下一轮会补，且 part 可续传省流量，但会白白浪费一次）。只有在确认连接半开挂死时才杀，且要预期到会新增若干 `[FAIL]`。

### 4.3 ★ `[FAIL]` 不重试，必须用循环包装
主脚本遇到 `[FAIL]`（下载截断 `curl 18`、连接重置 `curl 56`）只跳过、不重试，`done` 只记成功分片。单跑一轮会永久缺几个百分点。
**修法**：用 `run_danbooru_loop.cmd` 做 6 轮 `for /l`，每轮 `todo` 只含不在 `done` 里的分片，失败的自然被下一轮补上（`0013.tar` 就是这样补成功的）。

### 4.4 ★ `anlia2_flat_2mp` 是 mirror 布局
一个画师一个文件夹，`Get-ChildItem -File`（非递归）在顶层返回 **0 个文件**，会误判成「2MP 没跑出来」。必须 `-Recurse` 或 `os.walk`。（这个坑当场误导过一次。）

### 4.5 执行机是 PowerShell 5.1，脚本必须纯 ASCII
无 BOM 的 UTF-8 中文注释会被按 ANSI 解析成乱码，直接语法错误。含中文的脚本要：内容与中文路径都 base64 化，`[IO.File]::WriteAllText` 用 `UTF8Encoding($true)`（带 BOM）写盘，否则记事本打开是乱码。

### 4.6 统计口径
- 日志里的 `dl=xx MB/s` 是单值覆盖的旧值，**不可信**，要用两次采样算
- `shard-*.tar` 的 `%MB` 取整会把刚创建的文件显示成 0
- 源的 `src=N/1000` 天然滞后于输出片数（一个源分片约产出 1.5 个输出片）

## 4.7 第三路任务：danbooru 2MP 训练包

**为什么有这一路**：768 版是分发用的，**2MP 才是自己训练的**；训练机带不动 4MP 源，所以要把源图压到 2MP。原始 4MP 只当原料，不直接进训练。

**实现**：`%TEMP%\process_2mp.py` + `%TEMP%\run_2mp_loop.cmd`，日志 `K:\anlia\build_2mp.log`

- 输入：**复用** `I:\anlia2\danbooru\images\*.tar`（不重新下载，省 1.6 TB 流量）
- 输出：`K:\anlia\danbooru2024_2mp\shard-XXXXXX.tar`（1750 MB 封口，成员 `<id>.webp`）+ `manifest.jsonl`
- **★ 核心优化**：`面积 <= 2MP` 的图**原样复制字节**（不解码不重编码，零损失且快），只有超 2 MP 的才 LANCZOS 缩到 2MP 预算并 32 对齐重编码 webp
- 实测比例：copy 61% / scaled 39%（源平均 1.93 MP，但分布很宽，4.2 MP 是上限）
- 产物校验：`out_MP` 平均 1.32、**最大 2.00，无一超标**；平均 168 KB/张
- 体积预估：约 780 万张 × 168 KB ≈ **1.3 TB**（放 K 盘；K 剩 2340 GB，768 后续还要约 430 GB，合计后余量约 600 GB —— **偏紧，要盯着**）
- 速率实测：40 进程约 167 img/s（与 768 任务并行时）
- 断点：`K:\anlia\danbooru2024_2mp\_state.json`（done / sealed / manifest_bytes）
- 与 768 并行：2MP 吃 CPU、768 吃带宽，理论上互补；但两者都读 I 盘源 tar，会有 I/O 竞争

**注意**：`run_2mp_loop.cmd` 是 10 轮、每轮间隔 5 分钟的循环。因为源分片是边下边处理的，第 1 轮只覆盖当时已下好的部分，后续轮次自动补新出现的分片。
